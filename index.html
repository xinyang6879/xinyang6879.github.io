浏览器任务队列

Posted on 2026-02-17 In 前端

浏览器任务执行顺序

浏览器任务分为微任务（Promise、）、宏任务（同步任务也算宏任务的一种、setTimeout等定时器）、页面更新

  1. 执行当前同步代码（当前调用栈）。
  2. 进入循环后，取一个 task（宏任务）执行完。
    例如：setTimeout 回调、点击事件回调、script。
  3. 做一次 microtask checkpoint：清空所有微任务。
    例如：Promise.then、queueMicrotask、MutationObserver。
    微任务里新加的微任务也要继续执行，直到队列为空。
  4. 如果到渲染时机，浏览器进行渲染：
    requestAnimationFrame 回调 -> 样式计算 -> 布局 -> 绘制 -> 合成（UI 更新在这里发生）。
  5. 如有空闲时间，可能执行 requestIdleCallback
  6. 再取下一个宏任务，重复 2-4。

不是按照同步任务、微任务队列、渲染任务、宏任务的顺序执行，

而是先取一个宏任务（同步任务是放在宏任务队列的），然后再执行微任务、渲染任务。

ui更新与渲染

  1. “16ms/60Hz”与任务队列

浏览器刷新频率通常为60Hz，对应16.67ms一帧，但不同设备如120Hz刷新率

如果宏任务或微任务执行时间超过16ms，会错过当前帧，导致帧率下降甚至掉帧。微任务队列无限长会导致渲染和rAF回调一直被延迟（饥饿现象）。

requestAnimationFrame一般每帧调用一次，隐藏页面时会被节流或暂停。若执行时间超过下次垂直同步(vsync)时机，浏览器无法及时绘制，渲染延后。

也就是说最好的情况是每16ms执行一次，但浏览器无法保证。

  1. requestAnimationFrame
  • requestAnimationFrame会在“下一次重绘”之前执行，通常是每帧一次
  • 前台可见时，即使 UI 没有变化，rAF 也*_可能继续执行_。并不是执行requestAnimationFrame后就一定会有ui更新
  • 如果页面后台/不可见，rAF 往往会暂停。
  • raf最少的执行时间间隔是一帧

pc、ios、安卓区别

高层顺序一致

  • PC / Android / iOS 都遵循 task → microtask →（可能渲染） 的顺序。

实现与策略差异

  • PC/Android Chrome：使用 Blink/V8（Chromium 事件循环实现）。
  • iOS Chrome：使用 WebKit/JSC（苹果要求），实现代码完全不同。
  • Android/PC 的后台/省电策略比前台更激进，任务队列可能被节流或冻结。
  • iOS 更倾向于后台挂起，导致后台任务几乎停止。

场景区别

  1. 前台可见（Active/Visible）
  • PC / Android / iOS：rAF、定时器、microtask、渲染均正常执行。
  1. 后台但未冻结/挂起（Hidden but not frozen/suspended）
  • PC/Android：
    • rAF 通常停止。
    • 定时器被节流/预算限制。
    • microtask 随 task 被节流而变慢。
    • 渲染通常停止或极少发生。
  • iOS：
    • 后台往往直接挂起，任务基本不执行。
  1. 冻结 / 挂起（Frozen / Suspended）
  • PC/Android：
    • 进入冻结后，计时器/事件回调/Promise 回调暂停。
    • Energy Saver 可能冻结 CPU 密集后台页。
  • iOS：
    • WebKit 挂起后台页面，任务基本不执行。

微前端

微前端（Micro-Frontends）是一种将大型前端应用拆分为多个可独立开发、独立部署、独立运行的前端子应用的架构思想

出现原因

在传统 SPA / MPA中，随着业务增长，会出现：

  • 项目体积巨大、构建慢

  • 多团队协作互相影响（改一处，牵一片）

  • 技术栈难以升级（历史包袱）

  • 发布风险大（一次发布影响全站）

微前端核心特性

特征 说明
独立开发 每个子应用一个仓库
独立部署 子应用可单独上线
技术栈无关 React / Vue / Angular 可共存
运行时集成 在浏览器中组合
团队自治 团队边界清晰

微前端实现分类

  • 特性
    1. 独立开发部署：每个子应用可以独立运行和部署
    2. 技术栈无关：React 和 Vue 应用可以共存
    3. 应用隔离：JS 沙箱和样式隔离防止冲突
    4. 应用通信：通过 props 和全局状态实现数据传递
    5. 按需加载：只加载当前激活的应用

react的任务及其优先级

Posted on 2025-10-30 Edited on 2025-11-05 In react

为什么要引入任务调度

React 15（之前）的痛点

  • 旧架构是 同步渲染：更新一旦开始，就会一直占用主线程直到完成。

  • 整个组件树的渲染是同步、不可中断的。

  • 一旦开始 reconcilation（协调）阶段，会从顶到底一次性完成所有 diff，再统一更新 DOM。

  • 假如树很大（几千组件），或者一次 setState 涉及大量组件更新，就可能导致：

    • 掉帧（jank）：浏览器无法流畅地进行布局和绘制（16.67ms一帧的规则被打破）
    • UI 卡顿：浏览器无法及时响应用户交互（点击、输入等），造成卡顿感。（无法响应用户输入）
    • 低优先级更新阻塞高优先级任务

React 团队需要一种方式：

“让渲染可以分片执行、可以中断、可以优先处理紧急任务（比如输入）。”

React Fiber（v16，2017）——为并发渲染奠基

Fiber 是 React 为了支持“可中断渲染（interruptible rendering）”而引入的虚拟执行单元。

Fiber 是 React 16 重构的核心，Fiber 并不是“任务调度器”，而是一种数据结构 + 渲染引擎重写。：

  • 将原本“递归渲染”的过程改成了“循环 + 可中断的任务单元”。

  • 每个组件对应一个 Fiber 节点，其中保存：

    • 更新优先级（lanes）
    • 指向父/子/兄弟 fiber 的指针
    • 待处理的 effect 列表

这样 React 就能：

  1. 拆分渲染为小任务单元；
  2. 渲染到一半可以暂停；
  3. 暂停后可以恢复；
  4. 或丢弃并重来。
  5. 可以多帧执行（time slicing）

但 Fiber 自身只定义了“怎么中断和恢复渲染”。

它还缺一个“什么时候中断”的机制。

总结

时间 版本 关键点
React 15 之前 同步渲染 无中断机制，主线程被长任务阻塞
React 16（2017） 引入 Fiber + Scheduler 为并发渲染奠基
React 17（2020） 架构稳定期 无新特性，内部重构
React 18（2022） 启用 Concurrent Features 并发渲染正式落地

Scheduler调度器和并发渲染

Scheduler是任务调度，用于控制“任务”在主线程中的执行顺序与优先级

并发渲染是控制“渲染过程”如何被拆分、暂停、恢复和放弃

并发渲染在渲染阶段利用 Scheduler 实现异步可中断的渲染

任务调度是并发渲染的使能技术之一，但并发渲染还包含Fiber架构、渲染逻辑等其他组成部分。Scheduler提供了并发渲染需要的”中断决策”能力。

任务调度器（Scheduler）——决定“何时执行”

React 在 v16 同时引入了 scheduler 包。

主要是为了解决一个根本矛盾：“JavaScript执行（特别是渲染计算）与浏览器渲染/用户交互争抢主线程资源”。

React的目标是实现“可中断的异步渲染”，而要实现中断和恢复，就必须有一个中枢系统来管理和协调哪些工作应该先执行，哪些可以后执行。这个中枢系统就是任务调度器。

核心目标：

  • 保证高优先级任务（如用户输入）能够及时响应。

  • 合理安排低优先级任务（如渲染离屏内容）的执行时机，避免阻塞主线程。

  • 利用浏览器的空闲时间进行工作。

Scheduler 的核心循环

shouldYield() → 检查是否快超过 5ms、是否有高优先级任务进来。

与Fiber交互：

  1. 触发更新：setState、ReactDOM.render等触发了一次更新。
  2. 调度器接手：调度器接收到一个更新任务，并为其分配一个优先级。
  3. 调度执行：调度器根据当前主线程的繁忙程度和任务的优先级，决定何时执行Fiber Reconciler的工作循环。
  4. Fiber Reconciler工作：工作循环开始，一次处理一个Fiber节点（一个工作单元）。
  5. 询问调度器：在处理完一个Fiber节点后，Fiber Reconciler会去询问调度器：“主线程还剩下多少空闲时间？是否有更高优先级的任务插队？”
  6. 决策：
    • 如果时间充足且无更高优先级任务，继续处理下一个Fiber节点。
    • 如果时间不够了，Fiber Reconciler会保存当前进度（中断），并将控制权交还给浏览器。
    • 如果有更高优先级任务到达，调度器会中止当前正在进行的Fiber渲染任务，让它为高优任务让路。
  7. 恢复：当浏览器空闲或高优任务完成后，调度器会重新安排之前未完成的Fiber渲染任务，从之前中断的地方继续执行。
  8. 提交：当所有Fiber工作单元都完成（即完成了Reconcilation，构建好了新的Fiber树），React会同步地、不可中断地执行DOM更新（Commit阶段）。

浏览器的任务队列的交互

不用浏览器原生任务队列原因

浏览器原生的宏任务/微任务模型（setTimeout/Promise.then）只是时间切片的一种手段，但它们有许多限制

  • 缺乏多级优先级控制

    浏览器只分宏/微任务，但无法表达 React 需要的细粒度优先级（Immediate / UserBlocking / Normal / Low / Idle）。

    React 需要在“用户输入”优先于“后台渲染”的情况下做抢占和插队，浏览器队列无法灵活做到这一点。

  • 跨浏览器行为差异 & 不可控

    requestIdleCallback 在不同浏览器上行为不同（甚至某些环境不支持）。依赖这些 API 会导致不可预测性。

    浏览器任务队列与渲染管线（compositing/paint）和事件顺序复杂交互，React 需要精确控制何时 yield。

  • 无法轻易中断长任务

    把工作拆进一堆 setTimeout(fn, 0) 并不能为 React 提供“按优先级抢占”的能力，也会引入大量调度开销和延迟（微小任务切换开销高）。

  • 需要集成 React 的优先级语义

    React 的优先级语义（lanes、startTransition、输入优先级）需要被 scheduler 理解并映射到执行策略里。浏览器的事件循环对这些语义一无所知。

  • 避免 starvation（饥饿）与保证实时粒度

    React 需要在短时间窗口（几 ms）内决定是否继续工作。自己计算 deadline（frameBudget）并根据 performance.now() 判断更精确。

交互

  • 定义了自己的优先级系统：Immediate, UserBlocking, Normal, Low, Idle 等。这比浏览器的“宏任务”和“微任务”两种粗略的优先级要精细得多。

  • 智能调度：调度器会根据优先级，决定将React任务（如组件的渲染/更新）放入浏览器的哪个时机执行。

  • 利用浏览器API：

    1. 对于最高优先级的任务，它会用 Promise.resolve().then()（微任务）或甚至同步执行来尽快处理。

    2. 对于普通优先级的任务，它会优先使用 MessageChannel（宏任务）来让出主线程，以便浏览器处理用户交互和渲染。

    3. 对于低优先级的任务，它会使用 requestIdleCallback（或其polyfill）来在浏览器空闲时期执行。

Scheduler 的职责：

  1. 维护任务队列（每个任务带有优先级与过期时间）
  2. 根据优先级选择下一个任务执行
  3. 利用浏览器空闲时间（requestIdleCallback / MessageChannel）执行任务
  4. 在需要时中断执行，让出主线程

也就是：

Fiber 负责“怎么做”，Scheduler 负责“什么时候做”。

表现依旧是同步渲染

react16只是增加了一个可中断的渲染逻辑，但是如果中断之后，无法接上中断之前的渲染东西，只能从头再来一次渲染

React16 做的核心改动是：

1、把递归渲染改成了循环（Fiber），可以分片执行

2、引入 Scheduler，使得渲染可以被打断（理论成立，但是未默认启用）

3、但 React 16 默认仍然是“同步模式”，只有 Suspense 或 startTransition 才会启用异步调度能力（而这些 API 在 16 时代还未稳定）

因此在react16的时候，只是把一个长任务拆分为多个小任务，但是正常更新的时候还是一口气执行完毕

那么在极端情况下，react16比react15会快些，但是在普通场景下，可能15与16差不多

React16 的优势是不卡顿，不是更快

并发渲染（Concurrent Rendering）——利用调度实现新能力

因此实际上，react18才真正给并发渲染，不卡顿的能力

但react16-17，是为React 18（2022）出现的并发渲染打基础，所以并发渲染是 Fiber + Scheduler 的成果

并发渲染不是单一技术，而是 Fiber（可分片的工作单元）+ Scheduler（优先级 & 时间片）在浏览器事件循环之上协同工作的一套运行时策略。 它把渲染拆成小单元，可暂停/恢复/放弃，优先处理紧急任务（例如用户输入），以保证主线程响应性，同时在 commit 阶段一次性同步应用副作用与 DOM 更新。

Lanes模型

Lane = 表示一种优先级/槽（类似车道）。一个 root 可以同时有多个正在等待的更新，这些更新被映射到不同的 lane。

用位掩码（bitmask）来表示哪些 lanes 正在 pending：pendingLanes 是一个整数，每一位代表一类优先级（或一条“车道”）。

  • 出现原因

    React 16 的 expirationTime（概念）

    在 React 16 的早期并发尝试里，给每次更新计算一个 expirationTime（数值时间戳/截止时间）。

    意图：更新有一个“过期时间”，越紧急的更新过期时间越早；调度器优先执行过期时间早的任务。

    局限：单一数值的优先关系比较粗糙，难以同时表达“多个并发更新属于不同优先级且能共存”的情形；也不容易高效合并/跟踪多个并发优先级。

  • 核心思想

    用一组位（bitmask）表示“哪些优先级的更新同时存在于 root 上”。每一位代表一种优先级 lane（或一类优先级槽）。

    一个 root 上的 pending lanes 可以同时包含多种优先级的更新（多个位同时为 1）。

    调度时选择最高优先级的 lane（通常是最靠前的一位或按优先级权重计算）去进行渲染；低优先级的 lane 会被延迟或合并。

  • 作用

    • 高效：位操作（AND、OR、XOR、取低位）快速，适合频繁判断/合并/清除。
    • 能同时表达多种优先级：不同优先级的更新可以并存（多位同时为 1）。
    • 便于合并/抢占：选出当前应执行的最高优先级 lane 非常快。

  • 优点

    • 可以并行追踪不同优先级的更新（例如：一个高优先级的输入更新，正在被处理；同时存在一个低优先级的数据加载更- 新）。
    • 更容易做“合并/抢占/丢弃”逻辑：当高优先级更新来临，低优先级 lane 可以被暂停或丢弃。而expirationTime 是“标量”（一个时间戳），当并发更新很多并且频繁变更时，计算/合并逻辑复杂且不够灵活。
    • 位操作高效（快速判断、合并）。·

  • 合并、抢占与过期

    • 合并：若多个更新落到同一 lane，会被合并（同一位重复 OR 不改变值）。
    • 抢占：当高优先级更新到达，Scheduler 选出更高 lane 并暂停当前低优先的渲染（保存 nextUnitOfWork），转而处理高优先级 lane。
    • 过期策略：每个 lane 还可以映射到“过期时间”（expirationTime），用于当长时间没执行时强制提升优先级/执行。

流程

职责

  • 浏览器事件循环（宏任务 / 微任务 / RAF / requestIdleCallback）
    — 提供低级宿主回调、帧时机、空闲窗口。React 使用它们作为触发点（host callback），但不依赖其优先级语义。

  • Scheduler（React 的调度层，scheduler 包逻辑）
    — 维护任务队列与 timer 队列、计算是否该让出（shouldYield()）、选择哪个优先级的任务执行、通过 MessageChannel / postMessage / RAF / setTimeout 等 host API 调度执行。暴露 runWithPriority / scheduleCallback（内部使用不稳定 API）。

  • Lane 模型（React18 的优先级表示，bitmask）
    — 在 root 上用位掩码表示哪些优先级的更新 pending。快速选择最高优先级 lane 进行渲染，支持并存、合并、抢占。

  • Fiber（可中断的渲染单元）
    — 每个组件对应一个 Fiber 节点。使用 current <-> workInProgress 双缓存，保存中间态、hooks 状态、effect tag、指针（child/sibling/return/alternate）。performUnitOfWork 是对单个 Fiber 的处理单元。

  • Render 阶段（可中断）与 Commit 阶段（不可中断）
    — Render：构建 / diff workInProgress 树，生成 effect list（可中断、可丢弃）。
    — Commit：把 effect list 原子性地应用到 DOM、执行 layout effects、update refs（不可中断，flush-before-paint）。

从setState到DOM更新大致流程

  1. 产生更新

    • setState, props change, 或外部事件触发更新。React 为此次更新分配一个 lane（基于事件类型与 API，如 startTransition）。将该 lane 的位 OR 到 root.pendingLanes。

  2. scheduleWork（调度请求）

    • React 调用 Scheduler 的 scheduleCallback(priority, flushWork)，确保在一个合适的宿主时机（MessageChannel/RAF/idle）运行 flushWork。

  3. Scheduler 触发执行（host callback）

    • Scheduler 在 host 回调中启动 performConcurrentWorkOnRoot(root)，并传入一个“时间截点/deadline”或自行用 performance.now() 计算 frameBudget。

  4. Render Phase（workLoop） — 可中断执行

    • workLoop 循环：while (nextUnitOfWork && !shouldYield()) { nextUnitOfWork = performUnitOfWork(nextUnitOfWork); }
    • performUnitOfWork 包含 beginWork（计算、diff、产生/复用子 Fiber）和在无子节点时 completeUnitOfWork（构建 effect list 并回溯）。
    • shouldYield() 基于 Scheduler 判断（超出 frameBudget，或有更高优先级任务到来） → 若为 true，则暂停 render，并把当前 nextUnitOfWork 保存在 root/workInProgress 上以便下次恢复。

  5. 被抢占 / 暂停 / 恢复

    • 如果在 render 中出现更高优先级更新（例如用户输入），Scheduler 可能暂停当前低优先级 render，切换去处理高优先级 lane（选择 pickHighestPriorityLanes(root.pendingLanes)）。渲染中间态 workInProgress 保留或（在策略下）被丢弃并重建。

  6. Render 完成 / 进入 Commit

    • 当为 workInProgressRoot 选择的 lanes 的 render 做完（或到期/过期策略允许 commit），React 进入 commit 阶段。commit 是同步、不可中断的：apply DOM mutations、run layout effects、call lifecycle、update refs。

  7. 清理 pendingLanes / schedule 下轮工作

    • Commit 后清除已处理的 lanes（root.pendingLanes &= ~processedLanes）。若还有 pending lanes（或被暂停后仍有剩余），Scheduler 会 schedule 下一个 host callback 继续处理。

  8. 副作用（useEffect）异步运行

    • useEffect 的回调在 commit 后安排为异步任务（不阻塞绘制），而 useLayoutEffect 在 commit 阶段同步执行（因此 commit 不能中断）。

注意：

  • 浏览器任务队列只是宿主触发器：React 不把更新直接放进 setTimeout/microtask 然后依赖浏览器来优先排序。相反，React 的 Scheduler 决定优先级并在合适的宿主回调点（MessageChannel、postMessage、RAF、requestIdleCallback）触发自己的 flushWork。

    • MessageChannel 被频繁用作“最小延迟且跨浏览器稳定”的触发器（比 setTimeout 更低延迟、顺序更可控）。
    • requestIdleCallback 有时用于后台/低优先任务，但不可完全依赖（兼容/行为差异）。

  • Scheduler 决定何时 yield（让出主线程）：通过 performance.now() 与 frameBudget 或 host 提供的 deadline 评估是否应中断当前 render。浏览器在它的 event loop 中会在合适时机执行这些 host callbacks，所以 React 能在不阻塞浏览器帧渲染的情况下“占用小段时间再让出”。

  • 优先级插队（抢占）：当高优先更新到来，Scheduler 会优先处理其 lane，暂停低优渲染并保存中间状态。该抢占并不是浏览器原生“中断”任务，而是 Scheduler 在下一个调度点（或立即 if possible）触发高优任务而不是继续低优任务。

中断与恢复

核心：React 使用双链表 / 双缓存树（current <-> workInProgress）来做到“在不破坏当前 committed UI 的情况下准备新 UI”。这也是“可恢复”能力的基础。

  • 关键数据结构

    • Fiber 节点包含指针：return、child、sibling、以及 alternate（指向另一棵树上的对应节点）。
    • root.current 指向当前已提交的树（commit），workInProgress 指向正在构建的树（render phase）。
    • workInProgressRoot 保存当前渲染会话的根（以及 nextUnitOfWork 指针）。

  • 工作流程（保存/恢复）

    • 准备 workInProgress：

      当要开始 render 时，基于 root.current 克隆出 workInProgress（或复用 alternate）：workInProgress = createWorkInProgress(root.current).

    • 逐个 performUnitOfWork：

      每个 Fiber 的 beginWork 会读取 props/state，从 updateQueue 中弹出更新，生成子 fiber 等。

      如果时间片到期，会把当前的 nextUnitOfWork 保存在 workInProgress 上（或 root 上），然后 scheduleCallback 继续下次执行。

    • 暂停时保存点：

      因为 workInProgress 是独立对象，已做的变更（计算出的 props/children/effects）保存在它上面，下一次调度从 nextUnitOfWork 继续，不需要从头重建全部状态（只是对尚未执行的部分需要继续）。

    • 被抢占的恢复：

      若出现更高优先级更新，React 可以中止当前 workInProgress（它仍在内存），转去处理高优更新；之后再回来继续剩余的 workInProgress，或根据策略丢弃并重建一个新的 workInProgress（例如当数据变了太多时，会选择重来）。

  • 为什么能“恢复”

    • workInProgress 是渲染中间态的完整 snapshot（包含已构建的 Fiber 子树、effect list）。
    • 不像早期只能“暂停并从头开始”，现在可以从保存的 nextUnitOfWork 继续处理尚未完成的节点。这就是“恢复”。

  • 注意：

    1. Commit 阶段始终使用 workInProgress 完全生成的 effect list；commit 一旦开始，必须同步完成（见后面 commit 不能中断的原因）。

    2. 某些场景会丢弃 workInProgress（例如重要新的更新合并进来并改变了渲染目标），React 会创建一个新的 workInProgress 并放弃旧的，避免为过时计算浪费时间。

总结

任务优先级

优先级

  1. Immediate / Sync（同步）

    • 立即执行，typical: flushSync、React 内部在某些情况下强制同步提交（例如事件处理器里某些操作）。
    • 用于需要瞬时看到结果的操作（例如表单提交后的导航）。

  2. UserBlocking（用户阻塞 / 离散输入）

    • 针对用户输入（点击、键入），需要快速响应但允许短暂中断。
    • React 将离散输入赋予比普通更新更高的优先级以保证流畅。

  3. Normal / Default（默认）

    • 常规更新（例如数据返回后 setState）属于此类。

  4. Low（低）

    • 不紧急的后台更新（例如统计埋点的 UI 影响部分）。

  5. Idle（空闲）

    • 只有当主线程空闲才处理的任务（最晚执行）。

  • 根据事件类型分配优先级

    • 离散事件（例如点击、键盘按下）：通常分配较高的优先级（UserBlocking / Sync depending），以保持快速响应。
    • 持续性/拖动/滚动类事件：会分配连续输入的优先级，允许更频繁的更新但仍要保证流畅。
    • 非交互更新（例如数据加载、渲染大型列表）：通常为 Normal/Low，可以用 startTransition 明确把它们降为 Transition。
    • 后台/统计/日志写入：可安排到 Idle。

开发者手动修改优先级api

推荐常用（稳定 API）

  • flushSync()（来自 react-dom）最高优先级: 唯一一个提升的

    强制同步地立即执行更新（会导致当前更新不被时间切片中断）。慎用，仅在确实需要立即反映 UI 时使用（例如在事件处理流程中需要确保 DOM 已更新以测量布局）。

    • 属于 “同步优先级”（Sync / Immediate）。
    • React 会立即执行所有任务、立刻提交（commit）。
    • 会 中断 React 的时间切片机制，不允许被打断。

    常用于：

    执行 DOM 测量前的强制同步更新。

    保证状态立刻生效（例如强制让 UI 更新后马上计算尺寸）。

  • startTransition(() => { setState(...) })

    把一段更新标记为Transition（比较低优先级）。用于把非紧急更新降为低优先级（例如列表过滤、搜索结果渲染、页面切换动画后的内容加载等）。

  • useTransition() + isPending

    组合使用可以在 UI 上显示 pending 指示器。

    React 会给useTransition和startTransition更新打上一个 “transition lane”，这类更新：

    优先级低于 同步/用户输入。

    可被中断或延迟。

    一旦有更高优先级的任务出现（例如用户输入），会暂停并让更紧急任务先执行。

  • useDeferredValue(value)

    将某个值延后渲染，常用于防抖式渲染大型列表。

    属于 transition 内部的一种延迟机制；

    优先级 ≈ startTransition；

    但区别在于：

    useTransition 是手动包裹一段更新逻辑；

    useDeferredValue 是对现有值延后渲染。

  • 批量更新：React 18 里事件处理、Promise、setTimeout 等已被自动批处理，但仍可使用 unstable_batchedUpdates（来自 react-dom）做手动批处理（低级）。

不太常用 / 不稳定（低级）API（来自 scheduler 包）

  • scheduler 包里有 unstable_runWithPriority, unstable_scheduleCallback, 以及若干 unstable_*Priority 常量。它们能更细粒度地控制调度优先级，但是低级、不稳定 API。只有当你写自定义渲染器或需要非常精细的控制时才使用。示例：

capacitor将web项目打包为iOS/Android原生应用

Posted on 2025-10-30 Edited on 2025-11-12 In 前端

Capacitor 介绍

Capacitor 提供了一套统一的、以 Web 为中心的 API，使应用程序能够尽可能地遵循 Web 标准，同时还能在支持的平台上访问丰富的原生设备功能。

即，它可以把 web 端的项目打包为 app，从而在安卓/ios 上面作为一个 app 运行。

但 Capacitor 本质上只是Web 技术（Vue/React 等）+ 原生容器（WebView）= App，即它是通过在 app 中引入 webview 来进行支持的，与原生编写 app 还是有区别的，它用 WebView 包一层网页 → 在 App 里运行你的 Web App（HTML/CSS/JS），通过桥（bridge）调用原生功能。

与其他框架比较：

方案 原理 优点 缺点
手动 WebView 自己嵌网页 简单、可控 无桥接、维护重
Capacitor Web + 桥接层 快速、生态强、可扩展原生功能 性能略逊
NativeScript-Vue / React Native / Flutter JS/TS → 原生控件 原生性能、体验优 需重写前端逻辑
Tauri/Electron 桌面 Web 壳 跨平台桌面应用 体积大、移动端不可用

  • 控制页面内容显示在状态栏下方，即状态栏不遮挡内容

    • 内容会始终考虑设备的安全区域边缘

    • 系统会根据Android版本和设备特性自动决定是否启用边缘到边缘显示

    • 在支持的设备上，应用可以延伸到屏幕边缘，包括系统导航栏和状态栏区域

    • 实现类似iOS的沉浸式体验，但根据Android系统规则自动适配

svg在ios浏览器上显示模糊或者黑掉

表现

在安卓和pc端的浏览器显示是没有问题的，但是在ios的浏览器会显示非常模糊或者黑掉

原因

iOS Safari 的 SVG 渲染有以下几个已知 Bug：

  • SVG 内部有 filter（阴影、模糊、mask）或使用 引用时，Safari 会在 GPU 渲染下出现黑屏。

  • 如果使用 ，Safari 会自动进行栅格化（rasterization），导致缩放模糊。

  • width / height 属性不匹配 viewBox 时，会导致失真或黑屏。

  • 换为png或者其他格式

  • img改为object标签使用
